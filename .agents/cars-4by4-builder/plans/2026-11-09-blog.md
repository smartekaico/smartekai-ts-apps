# Blog of buying guides — Implementation Plan

> For agentic workers: use superpowers:executing-plans. Steps use `- [ ]`.
> Spec: `.agents/cars-4by4-builder/specs/2026-11-08-blog-design.md` (Spec 8). Read it first,
> especially §2, the content rules.

**Goal:** `/blog` with Markdown articles whose product, build and call-to-action cards come
from the live catalogue, then 6 launch articles, each approved by the user.

Two parts: **A, the blog engine** (code), then **B, the articles** (one at a time, each
approved before it goes live).

## Ground rules

- Your own git worktree, branch `feat/cars-blog` from `main`. Never commit to `main` or
  change branch in the shared checkout.
- Gate: `npx turbo run type-check lint build --filter=cars-4by4-builder...`.
- No schema change, no DDL, **no Gemini calls** (images reuse build photos and part
  illustrations).
- New dependencies only with `npm install <pkg>@<exact version> -w cars-4by4-builder`, as
  **devDependencies** if used only at build time. Never edit the lockfile by hand.
- Tailwind only scans `src/components` and `src/routes`: article styles go there.
- **Ask first:** merge, deploy, and **publishing any article** (removing `draft: true`).
- **Testing is required.** Use headless Chrome (command in
  `plans/2026-11-07-mvp-no-ai-renders.md`). If you can't test something, stop and ask
  before merging. Log what was tested and how.

## Part A — the blog engine

### A1. Markdown to modules at build time

- [ ] `apps/cars-4by4-builder/content/blog/` with one sample post, `draft: true`, using all
  three shortcodes.
- [ ] A small Vite plugin (in `apps/cars-4by4-builder/vite/blog-plugin.ts`, imported by
  `vite.config.ts`) that turns each `.md` into a module exporting:
  - `meta`: frontmatter, typed (title, description, vehicle?, category?, published, updated,
    draft, hero);
  - `blocks`: an array of `{ type: "html", html }`, `{ type: "product", id, vehicle? }`,
    `{ type: "build", slug }` and `{ type: "cta", vehicle }`, in order. Shortcodes split the
    HTML, so React renders cards between HTML chunks: no DOM-patching, no hydration issues.
- [ ] Use `marked` (or similar) plus a frontmatter parser, at build time only. The Worker
  never parses Markdown.
- [ ] **Validation at build time.** Import `seedParts`, `seedVehicles` and `seedPresets` from
  `src/seed/` and fail the build with the file and line on: an unknown part id, vehicle or
  build slug; a product whose `vehicle` it doesn't fit; missing or invalid frontmatter; a
  duplicate slug; a hero that doesn't resolve. (Curated build slugs are preset slugs.)
- [ ] Spot-check: a broken shortcode fails `vite build` with a clear message; the sample
  builds.
- [ ] Commit `feat(cars): build-time Markdown for the blog`.

### A2. Data for cards

- [ ] A server function `getBlogCards({ partIds, vehicleIds, buildSlugs })` returning, for
  each part, `toPublicPart(part, vehicleLink)` per requested vehicle (so the Buy label
  matches what `/go` will use) and each build's photo, name, vehicle and total. One query
  per table with `inArray`, run with `Promise.all`.
- [ ] Commit `feat(cars): catalogue data for blog cards`.

### A3. Pages

- [ ] `src/routes/blog/index.tsx`: newest first, excluding drafts. Title, description, date,
  vehicle tag. `?vehicle=` filter using the gallery's labels. `pageMeta` for `/blog`.
- [ ] `src/routes/blog/$slug.tsx`: unknown slug → the normal 404. Layout:
  - title, dates ("Updated …");
  - **the disclosure box before any link** (spec §2);
  - hero (build photo with the studio crop in a clipping frame, or the part illustration);
  - blocks: HTML in a `prose`-style article (write the styles; no new Tailwind plugin unless
    it's tiny and the user agrees), and:
    - `ProductCard`: illustration with the "Illus." label, name, brand, "Est." price,
      install hours, fitment badge, and Buy on Amazon via `/go/<id>?vehicle=<id>` with
      `rel="sponsored nofollow noopener noreferrer"`. No button when there's no link;
    - `BuildCard`: reuse the gallery card;
    - `CtaCard`: "Plan your {truck} build" → `/build?vehicle=…&step=parts`;
  - "Related builds" for the post's vehicle, and the CTA, at the end.
- [ ] **Drafts:** not listed, not in the sitemap, 404 normally. With `?preview=1` they render
  with a "Draft — not published" banner and `noindex`, so the user can review on a phone.
- [ ] Meta: `pageMeta` (title, description, canonical, hero as share image) plus JSON-LD
  `Article` (headline, datePublished, dateModified, image, publisher "Overlander Builder").
  No `Review` or rating markup.
- [ ] `sitemap.xml`: add `/blog` and each published post with `<lastmod>` from `updated`.
- [ ] Header: "Guides". Home: a "Buying guides" strip with the 3 newest published posts,
  hidden when there are none.
- [ ] Commit `feat(cars): blog pages`.

### A4. Verify the engine

- [ ] Sample post at 375 px and desktop with `?preview=1`: disclosure first, cards correct,
  Buy links go to the right ASIN for the vehicle, a part without a link shows no button.
- [ ] Without `?preview=1` the draft 404s, and it's absent from `/blog` and the sitemap.
- [ ] Share tags, canonical URL and JSON-LD present (read the page source).
- [ ] `/blog` and a post: CPU from `wrangler tail` after deploy, 10 warm requests, p50 under
  10 ms.
- [ ] Gate passes; `npx wrangler deploy --dry-run --outdir /tmp/cars-dry`.
- [ ] Ask to merge and deploy the engine with **no published posts** (only the draft sample).

## Part B — the articles

The six launch titles are in spec §6. Write them **one at a time**.

### Per article

- [ ] Before writing: run `npm run links:check -- ./scripts/parts-links.template.csv`
  (against production, read-only) and use only parts with working links for the post's
  vehicle; note parts with no link as "no link yet" rather than linking elsewhere.
- [ ] Write it per spec §2 and §3:
  - 1,200–2,000 words, one H1 (the title), clear H2 sections, plain language;
  - 3–6 `product` cards, 1–2 `build` cards, one `cta`;
  - **no "we tested", no invented experience, no Amazon prices or ratings**; fitment
    caveats wherever products are vehicle-specific;
  - facts from manufacturer specs and our catalogue; if unsure, leave it out or say it
    depends;
  - `draft: true`.
- [ ] Self-review against spec §2, line by line, and fix anything that fails.
- [ ] Commit `docs(cars): blog draft — <title>`, deploy (drafts stay hidden), and send the
  user the `?preview=1` link with a 3-line summary of what the article recommends.
- [ ] **Wait for the user's approval or edits.** Apply edits; on approval, set
  `draft: false` and the dates, commit `feat(cars): publish — <title>`, then ask to deploy.
- [ ] After publishing: the post appears in `/blog`, the home strip and the sitemap; its
  Buy links work; share preview shows title and image.

### After all six

- [ ] Ask the user to submit the sitemap again in Search Console (or request indexing for
  each post).
- [ ] Log in `.agents/logs/`, current-work line in `plans/active.md`.

## Done when

Spec 8 §8 holds, each article was approved by the user before publishing, results are
logged, and merges and deploys had the user's OK.
